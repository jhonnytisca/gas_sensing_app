# Gas Sensing App

A PyQt6 application for gas sensor acquisition. Configuration, instrument drivers,
experiment sequencing, storage, and the user interface are separate modules.
Mock devices support development and testing without connected instruments.

## Experiment configurations and device ports

Use **Load config**, **Save config**, and **Devices** beside **Results** in the top
panel. Saved YAML configurations include measurement and gas settings, logging
preferences and shutdown flows. **Save config** asks for a name and creates
`workspace/configurations/<name>/<name>.config.yaml`, with the selected recipe copied as
`<name>.recipe.yaml` in the same folder. Transfer the whole folder together. Existing
names require confirmation before replacement; manual configurations without a
selected recipe contain only `<name>.config.yaml`. The local `workspace/` directory
is ignored by Git. A complete tracked example is available in
[`src/gas_sensing_app/assets/configuration.example/`](src/gas_sensing_app/assets/configuration.example/).
Ports and serial transport settings stay in each
computer's local application settings and can be selected or entered in **Devices**.
Loading never starts an experiment. See the
[configuration workflow](src/gas_sensing_app/assets/manual/operator-guide.md#save-and-load-experiment-configurations)
for details.

## Operator guide

See the [Operator guide](src/gas_sensing_app/assets/manual/operator-guide.md) for
connections, laboratory configuration, a first simulation, manual measurements,
complete recipes, gate sweeps, and troubleshooting. The same guide is available
through **Operator guide** in the application.

For a 2400 run, see [fixed-voltage configuration and measurement steps](src/gas_sensing_app/assets/manual/operator-guide.md#configuration-for-a-2400-fixed-voltage-measurement).
The guide includes port discovery, Linux serial permissions, instrument settings,
GUI/YAML controls, shutdown, and troubleshooting voltage mismatch and overflow.

The workspace separates **Measurement**, **Gases**, and optional **Gate** setup.
Start and Stop remain visible. Narrow windows offer separate preparation and live
reading views. Dark and Light buttons update the controls and all plot colors.

## Running the application

Use Python 3.10 or later. From the project directory:

```bash
uv sync --group dev
uv run sensor
# List instrument ports, or generate YAML entries interactively:
uv run find-ports
uv run find-ports --yaml
# Load an existing configuration explicitly:
uv run sensor --config /path/to/laboratory/config.yaml
```

Alternatively, install with `pip install -e .` and run `sensor`. Conda users can
run `conda env create -f environment.yml`, then `conda activate gas-sensing-env`.
`environment.yml` delegates application dependencies to `pyproject.toml`;
`uv.lock` pins the environment used by `uv sync`. These installation files belong
in Git and are not generated by the application.

### Workspace and first startup

Running `sensor` without `--config` creates this layout in the launch directory:

```text
workspace/                         # Local files; ignored by Git
├── settings/
│   ├── config.yaml                # General startup settings
│   └── failure_gases.yaml         # General shutdown flows
├── configurations/                # One folder per saved experiment
├── recipes/                       # Working recipes
├── data/                          # Recorded results
├── console_logs/
└── logs/
```

Missing general settings are copied from the installed templates in
`src/gas_sensing_app/assets/defaults/`. A fresh installation starts in simulation,
with unassigned ports and zero shutdown flows. Review shutdown flows for your
setup before real measurements. Existing or invalid files are never replaced by
defaults; invalid YAML/settings produce an error. An explicitly supplied `--config`
must exist and have valid dependencies; a typo does not generate new files.

The previous root-level files and folders are not read, imported or moved.
Migrate existing settings and recordings manually into this layout. The files
`workspace/settings/config.yaml` and `workspace/settings/failure_gases.yaml`
are the active general settings.

Within a workspace, relative output paths are resolved from `workspace/`, even
when loading an experiment from a nested folder. Recipe and shutdown-file
references remain relative to their configuration file. Absolute output paths
remain unchanged. Explicit configurations outside a workspace use the launch directory's
`workspace/` for output; loading a configuration keeps the active workspace. Results preview uses the same paths and never generates settings.

Startup does not open instrument connections. Measurement and gate settings are
locked during a session; manual gas settings can be updated between complete
sweeps. Local device connections remain in the operating system's user settings.
Only the selected measurement instrument is connected when acquisition starts.

## Measurements and channels

| Setup | Readings and connections |
| --- | --- |
| Keithley 2400 | R, V, and I returned by the instrument, using automatic resistance or constant drain voltage; 2/4 terminals |
| 2700 + 7706, 2 terminals | Resistance or voltage per channel, H/L, channels 1–20 |
| 2700 + 7706, 4 terminals | Resistance using pairs 1/11 through 10/20; force H/L and sense H/L |

The card slot number can be 1 or 2. For example, `101` is channel 1 in slot 1;
a Kelvin sensor uses `sensor_id=101` and `sense_channel=111`. `sensor_id` identifies the
sensor/channel, **not the instrument**. The 2400 uses `single`.

The 7706 does not provide a direct current measurement path to the 2700 ammeter.
Its channels 21 and 22 are digital outputs. The application does not infer current
or voltage from a resistance reading. In 2700 mode, unavailable quantities are
left empty and the reason is recorded in `measurement_status`.
Measuring R/V/I for each sensor in this setup requires a different physical
measurement path; software alone cannot provide a current input.

The drivers are based on the
[Keithley 2400 manual](https://download.tek.com/manual/2400S-900-01_K-Sep2011_User.pdf)
and the [7706 manual for the 2700](https://download.tek.com/manual/PA-719E_Mar2015_7706.pdf).
Automated tests do not replace validation with the laboratory instruments.

## Gate control and recipes

The EA-PS supplies the **gate**, independently of the 2400 drain voltage.
Fixed voltages and ascending/descending sweeps can be programmed with a positive
step size, settling time, and current limit. The interface limits the gate to
0–65 V; a lower limit can be configured through `gate.max_voltage`.

Sequencing works with `MockGateSupply`. Physical communication with the EA-PS is
pending identification of the installed interface. In real mode, enabling the
gate without a verified transport is rejected before opening any instruments.
To integrate it, implement `GateSupply` and inject `gate_transport_factory` into
`HardwareFactory`; the `EAPS3065` adapter delegates operations without assuming SCPI.

Each recipe step performs the following sequence:

1. Apply gas flow setpoints and the shutter state.
2. Set each gate point and wait for `dwell_s`.
3. Acquire and save each sensor reading while holding gas flow setpoints constant.
4. Complete the sweep before moving to the next step.

`duration` is the minimum stage duration. If the sweep takes longer, it is allowed
to finish; if it takes less time, the final gate point is held while acquisition
continues for the remaining duration. In manual mode, sweeps repeat until stopped;
gas changes are applied between sweeps. Without a sweep, `interval_s` sets the
target minimum acquisition interval, subject to instrument latency. Sensors are
measured sequentially and receive individual timestamps.

Examples are provided in `assets/recipe.template.yaml` and
`assets/gate_sweep.recipe.yaml` within the package. Recipes can override `gate`
settings per stage. Omitted gas channels have a zero flow setpoint.

## CSV output and plots

### Independent results previewer

Click **Results** beside the main window's theme selector, or run:

```bash
uv run preview-results
uv run preview-results --config /absolute/path/to/config.yaml
uv run preview-results --folder /absolute/path/to/measurements
```

The previewer is a separate process with no instrument connections. On each
launch it starts in the configured `logging.data_log.folder`, resolved against
the workspace. An explicit `--folder` overrides that startup default. Missing
configuration defaults to `workspace/data/` without generating settings.

- **Open folder / Open files:** replace the displayed CSV list by default. Choose
  **Add to displayed files** to append instead; duplicates are ignored. These
  options never replace files on disk. Subfolders are optional. Select one file
  at a time; use the list/arrow keys to move between measurements.
- **Sensors / Gas channels:** choose which curves to compare. A sensor without
  valid resistance still retains its associated gas readings.
- **R / V / I / Flow:** toggle plots; unavailable signals are disabled. Gas
  setpoints are dashed and reported flows are solid. Time is shown in minutes.
- **Spike-resistant view** is on by default. It fits Y axes using each curve's
  1st–99th percentiles, with padding, within the visible time window. It does not
  delete or smooth samples. Short series and gas setpoints retain full extrema;
  the footer reports how many plotted values are outside the current Y view.
  **Full view** includes all extrema. Wheel to zoom, drag to pan, or use the
  right-click axis controls; **Fit view** restores the full time interval.
- **Additional label:** optional text shown above the curves and included in PNG
  exports. It resets when selecting another file and does not modify CSV or JSON.
  Gas flows are displayed as stored, without preview scaling.
- **Full JSON** shows matching `.metadata.json` when available. Old CSVs
  (`device`, `step`) and new CSVs (`sensor_id`, `recipe_step`) are supported.
- **Export PNG** saves the current visible plots and zoom. **Reload file** refreshes
  a snapshot, including a file still being recorded; source data is never edited.

For Linux Mint, [preview-results.desktop](preview-results.desktop) is a launcher
configured for this checkout; use `workspace/settings/config.yaml` as its configuration. Copy it to your Desktop and
allow launching when prompted, or to `~/.local/share/applications/` for the menu.
If moving the project to another computer, update its `Exec` and `Path` entries
to that computer's `uv`, project, and configuration paths. The command is
registered in `[project.scripts]` in `pyproject.toml`.

### Recorded data

Each sensor reading produces one UTF-8 row with comma separators and a decimal
point. The row is written, then `flush()` and `fsync()` are called before notifying
the interface. Filenames include microseconds and a unique identifier; files are
created exclusively to avoid overwriting another session.

Each CSV has a matching `<same-stem>.metadata.json` containing initial settings,
sensor/channel mappings, slot/wiring, hardware configuration, gas ranges, recipe,
gate and shutdown settings. Keep both files together. Existing files retain their
original schema. Elapsed time starts after instrument preparation completes.

| Column | Meaning |
| --- | --- |
| `timestamp`, `elapsed_s` | ISO 8601 UTC timestamp and monotonic elapsed time |
| `recipe_step`, `sensor_id`, `sense_channel` | Recipe stage (or MANUAL), sensor identifier and optional sense channel |
| `resistance_ohm`, `voltage_V`, `current_A` | Electrical values returned by the instrument |
| `measurement_status` | `ok`, `simulated`, `overrange`, or `overrange_or_unavailable` |
| `resistance_range_mode`, `resistance_range_requested_ohm`, `resistance_range_actual_ohm` | Auto/manual, requested manual range, and instrument range readback when available |
| `gate_setpoint_V`, `gate_voltage_V`, `gate_status` | Requested gate voltage and available readback |
| `gas_N_NAME_setpoint_sccm`, `gas_N_NAME_actual_sccm` | Requested and actual flow for each gas |
| `shutter_open` | Requested state: 0/1; empty if disabled |

An empty field means no valid measurement is available; it is never replaced with
zero. ROD-4 flow readbacks are already in sccm and are saved without extra scaling.
`scan_id` starts at 1 for each session and increments for every sensor round,
continuing across recipe steps. All sensor rows in that round share the same ID.
A stopped or failed round may contain fewer sensors. Setpoint commands still use
percentage of the configured full scale; only readback scaling was removed.
All gate fields are empty when disabled. All configured gas channels are retained.
Electrical, gas, and gate readings are queried sequentially; they are not presented
as simultaneous acquisitions across instruments.

The four plots (R, V, I, and gases) share a time axis and retain up to 10,000 points
per curve on screen. The CSV retains the entire session. Gate values appear in the
voltage plot with their own labels. The layout adapts to narrower windows, and
panels support scrolling.

## Stopping and failure handling

Edit `workspace/settings/failure_gases.yaml` to define which gases should remain active:

```yaml
mfc_flows:
  1: 0
  2: 0
  3: 0
  4: 0
```

Values are in sccm; omitted channels are set to zero. The configuration is validated
and captured at startup, so editing it during a session does not change that
session's shutdown policy. The same profile applies on normal completion, when
STOP is pressed, when the window is closed, or when a failure is detected.

Shutdown first attempts to disable the gate and 2400 outputs, open the 2700
channels, close the shutter, apply each gas flow, and close communications.
Failure of one operation does not prevent the others from being attempted; errors
remain visible and are written to the console log when enabled. Closing the ROD-4
connection does not reset the purge profile to zero. Waits can be interrupted;
an ongoing hardware call is bounded by its timeout.

This covers failures caught by the application. A power outage, forced process
termination, or loss of communication prevents shutdown commands from being
guaranteed; those cases require protection independent of the software. Rows
already committed to disk are retained within the guarantees of the filesystem
and storage device.

## Architecture and collaboration

```text
main.py                              application composition and startup
config/models.py                     configuration contracts
config/config.py, validation.py      loading and validation
controllers/dashboard_controller.py  window actions and lifecycle
core/recipe.py                       gas stages and gate profiles
core/engine.py                       sequencing, acquisition, and shutdown
core/worker.py                       bridge between the engine and Qt
core/measurement.py                  common instrument reading model
core/storage.py                      persistent CSV storage
hardware/factory.py                  real/Mock selection per session
hardware/*.py                        drivers and gate adapter
hardware/mock_drivers.py             reproducible simulation
gui/dashboard.py                     view and controls
gui/widgets/plots.py                 plots with a shared time axis
```

Drivers do not import Qt. The engine accepts an injected factory for failure
testing or integration of other instruments. The interface does not send hardware
commands. To add an instrument, implement its operations, register it in the
factory, and add acquisition/shutdown tests; do not duplicate the acquisition loop.

```bash
QT_QPA_PLATFORM=offscreen uv run pytest
uv run ruff check src tests
uv run ruff format --check src tests
```

Tests cover Kelvin channels, missing data, sweeps and gases, persistence before
GUI updates, acquisition/shutdown failures, and window closure.
